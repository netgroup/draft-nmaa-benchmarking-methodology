Benchmarking Methodology for Network Management AI Agents on Brownfield Networks

Abstract

This document specifies a benchmarking methodology for Network Management AI Agent (NMAA) systems, software systems that receive an operator requirement and act on a network to satisfy it using AI models. It defines the test setup (system under test boundary, brownfield substrate, scenario generator, out-of-band observation, fault injection), the test procedures for comparing settings of one controlled factor at a time, the metrics (functional success, damage-free run rate, cost, recovery), the statistical treatment required for near-zero damage probabilities, and the reporting requirements. It complements the conceptual framework described in a companion research document and existing work on task-oriented metrics for AI agents in network operations.¶

1. Introduction

Benchmarking documents in the tradition of [RFC1242] and [RFC2544] give implementers and operators a common way to measure and compare devices under controlled, reproducible conditions. Network Management AI Agent (NMAA) systems, which configure and operate networks using AI models, need the same discipline, with two differences. First, the output of the system under test is a change to a network, and its most important failure mode, collateral damage to services that were already running, is only observable on a network that carries such services. Second, the system under test is stochastic: the same input can produce different actions, so results are proportions with uncertainty, and the regime of interest (damage probabilities near zero) requires appropriate statistics.¶

This document specifies how to run and report such benchmarks. The underlying model, the controlled factors and the rationale are described in [FRAMEWORK]. Task-oriented metrics for AI agents in network operations are proposed in [I-D.contreras-bmwg-ai-agent-benchmarking]; this document reuses them where applicable and adds the test setup, the collateral-damage metric, the paired procedures and the statistics. Terminology for the system under test boundary follows [I-D.gaikwad-llm-benchmarking-terminology].¶

1.1. Scope

In scope: configuration and change tasks performed by an NMAA system on an emulated or laboratory network; comparison of settings of one controlled factor (model, abstraction level of the agent-network interface, agent mode, task class) under a matched budget. Existing task sets, such as those of [I-D.cui-nmrg-llm-benchmark], can be run under this methodology once placed on a brownfield substrate.¶

Out of scope for this version: troubleshooting and root-cause tasks (TODO: whether to include them), adversarial testing of agents, and performance of the inference serving layer (covered by [I-D.gaikwad-llm-benchmarking-methodology]).¶

As for the benchmarking documents of the former BMWG [RFC6815], the procedures are intended for isolated laboratory environments only.¶

This document adds:¶

Cell:

The set of runs sharing one setting of every controlled factor and stress parameter.¶

Paired runs:

Runs of different settings of the factor under study on the same task variant (same request, same generated brownfield, same fault seed).¶

Outcome label:

One of clean success, dangerous success, clean failure, destructive failure, assigned to each run (Section 5).¶

3. Test Setup

3.1. SUT Boundary

The SUT is the NMAA system between the HAI and the ANI, including the model(s), the orchestration logic and the ANI adapter. The substrate, generator, fault injector and observer are outside the SUT. The tester MUST declare the SUT boundary and MUST NOT compare results obtained at different boundaries.¶

5. Metrics

5.1. Functional Success

Definition: a run is a functional success if the requested service passes all its task test cases at the end of the run.¶

TODO: hard (structural) and soft (semantic) success, aligned with [I-D.gaikwad-llm-benchmarking-profiles].¶

5.2. Damage-Free Run Rate

Definition: a run is damage-free if, after the run, every baseline invariant of every pre-existing service instance and every global invariant still holds. The damage-free run rate of a cell is the fraction of its runs that are damage-free.¶

Discussion: the unit of damage is the service instance; an instance is damaged if any of its invariants fails, counted once. The per-run outcome is binary because collateral damage is a zero-tolerance property in operations. The magnitude of damage (fraction of damaged instances per service class) is a secondary, diagnostic measure.¶

5.3. Outcome Labels

Each run is labeled clean success (functional success, damage-free), dangerous success (functional success, not damage-free), clean failure (no functional success, damage-free) or destructive failure (neither).¶
